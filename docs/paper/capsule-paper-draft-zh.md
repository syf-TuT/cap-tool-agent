## 摘要

代码即策略（Code-as-Policy，CaP）使大语言模型能够以 Python 程序组织机器人感知、规划与控制，但程序执行一旦改变机器人、物体或环境状态，一般软件修复中的回滚与历史片段重放便不再自然成立。针对这一问题，本文提出运行时控制系统 Capsule，并将其核心机制定义为效应边界前向恢复（effect-bounded forward-only recovery）。Capsule 保留 CaP 原有机器人函数接口，在运行时将程序划分为效应边界执行单元，使用持久命名空间逐单元执行，通过原语调用追踪生成源代码绑定反馈，并以副作用账本记录已经产生物理影响的历史单元。若执行失败，系统禁止补丁后重放历史副作用，要求追加的恢复代码先调用环境声明的新观测函数，再从当前物理状态继续执行。本文基于 Robosuite 中的 Cube Stack、Cube Restack、Two-arm Lift 与 Two-arm Handover 任务审计现有实验记录。结果显示，在“每个种子选取最新运行”的重试包容协议下，Cube Stack 完成 17/20 个种子；在协议一致的 Two-arm Lift 两批实验中，Capsule 完成 11/20 个种子；Cube Restack 完成 4/20，而 Two-arm Handover 的两个主要版本均未完成任务。上述结果验证了系统在多类操作任务上的可运行性，同时表明其效果具有明显的任务和协议依赖。由于现有基线与 Capsule 运行在不同提交、调用模式或重试规则下，本文不据此声称前向恢复提高了任务成功率。当前证据主要支持一种面向不可逆机器人程序的恢复约束和可观测运行时实现；其相对性能、恢复有效率与真实机器人外部效度仍需统一实验验证。

**关键词：** 代码即策略；智能体式机器人学习；运行时控制；前向恢复；程序修复；具身智能

## 1 引言

大语言模型驱动的机器人智能体正在从一次性动作预测扩展到程序生成、闭环执行与策略自改进。在本文限定的文献中，ASPIRE、ENPIRE、GaP 与 RATS 虽然分别更新程序修复经验、训练策略、计算图和技能记忆，但都以反复执行、获取反馈并修改决策对象作为自改进接口 [S01, S03, S04, S05]。这种闭环使系统能够利用运行时证据处理初始程序未覆盖的状态。然而，不同工作中的“反馈”和“修复”具有不同粒度：有的方法保存原语级轨迹，有的方法依赖任务奖励或仿真排练，还有的方法将成功代码或失败条件写入长期记忆。因而，闭环本身并不能说明系统如何处理已经发生的物理副作用。

这一问题在 CaP 系统中尤为直接。CaP 以普通程序组合感知、逆运动学、轨迹规划和夹爪控制函数。与纯软件程序不同，机器人程序中的移动、抓取和释放会改变世界状态。假设某一抓取片段已经闭合夹爪并移动了目标物体，此时修改该片段的源代码并再次运行，并不会自动恢复它最初面对的物体位姿、机器人关节和夹爪状态。若运行时仍把历史代码当作可任意重放的软件片段，程序状态与物理状态可能发生偏离。真实机器人自改进还依赖安全、验证和场景重置基础设施 [S01, S03]，因此“能否修改代码”与“修改后能否从正确的物理前置状态执行”是两个不同问题。

现有文献为细粒度反馈、结构化表示和长期经验提供了重要基础。ASPIRE 与 RATS 表明，步骤级轨迹和验证信号能够支持局部失败诊断与代码修复 [S01, S05]；GaP 通过带接口契约的计算图组织可执行技能 [S04]；ENPIRE 则将自动策略研究置于真实机器人反馈闭环中 [S03]。与此同时，结构化 API 也会把系统的能力上界绑定到已有原语和符号模型 [S01, S02, S05]。这些研究没有形成一个可以直接用于本文的统一恢复协议：不同系统更新的对象、反馈粒度、重试规则和物理状态假设并不相同，其成功率也不能直接横向比较。

本文关注以下研究问题：**当 CaP 程序包含不可逆或不可安全回放的机器人副作用时，运行时如何在保留原有代码接口的同时，将失败修复约束为基于当前状态的前向恢复？** 为回答这一问题，本文设计 Capsule。系统不把机器人原语转换为规划器可选择的工具；模型仍生成调用原有 API 的 Python 程序。Capsule 在代码与环境之间增加运行时控制层，对代码进行元数据式分段，追踪实际原语调用，将错误与状态证据绑定到具体源码范围，并禁止已经产生机器人副作用的执行单元被再次运行或补丁后重放。恢复代码只能追加到程序中，并且必须先调用环境声明的新观测函数。

本文的贡献如下：

1. 提出效应边界前向恢复约束，区分尚未执行的可修补代码与已经改变物理世界的历史副作用单元，并明确不依赖任意物理回滚的机器人程序恢复语义。
2. 设计并实现 Capsule 运行时。该系统在不改变 CaP 机器人函数接口的条件下，提供效应边界执行、持久命名空间、原语追踪、源代码绑定反馈、副作用账本、禁止重放和基于新观测的追加恢复。
3. 对多个 Robosuite 任务的真实实验档案进行协议审计，报告任务完成、奖励、预算耗尽和缺失结果，并揭示当前系统在 Cube Restack、Two-arm Handover 等任务上的失败边界。本文同时说明现有基线为何不足以支持相对性能结论。

## 2 相关工作

### 2.1 执行反馈与任务内自改进

智能体式机器人方法可以按执行反馈如何进入更新过程进行区分。ASPIRE 记录细粒度多模态执行轨迹，由执行智能体反复生成、运行、诊断和修复机器人代码，并将验证后的修复经验沉淀为技能 [S01]。RATS 采用写入—执行—验证—诊断循环，在任务到来前自主练习，分别保存成功代码技能与失败记忆 [S05]。两者均说明步骤级证据可以支持局部诊断，但其目标分别是任务后的修复技能发现与任务前的自主技能获取。

ENPIRE 将编码智能体的策略改进放入真实机器人集群，通过环境构建、策略改进、回放和进化协作组织物理自动研究 [S03]。其结果同时揭示扩展机器人—智能体数量带来的墙钟时间收益和 token 成本、单机器人利用率之间的权衡。GaP 则用有向计算图表示策略，由多智能体选择带类型契约的技能节点，并在内部仿真中排练和修改图 [S04]。这些方法均需要反馈闭环，但更新对象分别为源代码及经验、训练策略和计算图。由于任务、预算和成功协议不同，它们的数值结果不宜直接比较。

Capsule 与上述方法的关系主要体现在运行时层面。它不负责发现跨任务技能，也不训练新的策略参数，而是约束一段已经生成的 CaP 程序如何执行、诊断和恢复。本文把“程序文本可修改”与“物理动作可回放”分开处理，重点解决历史副作用单元的恢复合法性。

### 2.2 经验载体与结构化策略表示

文献中的可复用经验具有不同载体：ASPIRE 保存语言化的失败修复技能，RATS 保存可执行代码函数和失败记忆，GaP 组合带类型契约的图节点，ENPIRE 迁移训练经验与策略研究结论 [S01, S03, S04, S05]。这些载体的粒度、可执行性和验证方式并不相同，不能无条件统称为同一种“技能”。

结构化表示通常在可控性与表达范围之间形成权衡。PDDL、固定机器人 API、原子控制器和图节点能够提供清晰接口或静态检查，但也限制新可供性和低层灵巧行为的表达 [S01, S02, S05]。Capsule 保留环境原有 API，并仅在执行元数据层建立边界。执行单元的源码始终由原始代码区域按顺序拼接，分组过程不重写、重排或展开程序。这一选择避免把运行时分组误写为新的机器人策略语言，同时也意味着 Capsule 的行为能力仍受底层 API 限制。

### 2.3 物理闭环、恢复与评价

真实机器人上的自主迭代需要安全约束、自动验证和场景重置 [S01, S03]。现有语料对仿真到真实的证据强度也不同：ASPIRE 与 RATS 主要报告有限任务上的技能提示迁移，GaP 报告仿真优化图的真实执行，ENPIRE 则直接在真实机器人上进行闭环策略改进 [S01, S03, S04, S05]。因此，不能把“在仿真中能够继续执行”直接等价为“可安全部署到真实机器人”。

评价指标也应与研究问题对应。除任务成功率外，现有研究还考察迁移、价值一致性、行为多样性、token/机器人利用率以及持续吞吐量 [S01--S05]。ValuePlanner 的价值增益、偏好一致性和动作多样性适用于无固定外部任务的主动行为 [S02]，但并不是 Capsule 的直接指标。本文主要考察任务完成、奖励、恢复行为、执行预算和失败类型，并强调首次尝试与重试后结果必须分开报告。

## 3 问题定义

### 3.1 CaP 程序与执行状态

给定任务指令 $x$、机器人环境 $\mathcal{E}$ 及其公开函数集合 $\mathcal{A}$，语言模型生成 Python 程序 $P$。程序由有序原子代码区域组成：

$$
P = (r_1, r_2, \ldots, r_n),
$$

其中每个 $r_i$ 对应一个顶层抽象语法树（Abstract Syntax Tree，AST）语句及其源码范围。运行时维护 Python 命名空间 $\Gamma_t$ 和物理环境状态 $s_t$。执行区域 $r_i$ 可写为：

$$
(\Gamma_{t+1}, s_{t+1}, e_t) = \operatorname{Exec}(r_i, \Gamma_t, s_t),
$$

其中 $e_t$ 表示返回值、标准输出、异常和原语调用轨迹等执行证据。

环境 API 为公开函数声明副作用集合 $\mathcal{A}_{\mathrm{eff}} \subseteq \mathcal{A}$。若区域的直接调用或可静态解析的辅助函数调用可能到达 $\mathcal{A}_{\mathrm{eff}}$，则该区域具有结构化副作用标记。运行时还根据实际追踪到的原语调用判断副作用是否真正发生。结构化标记用于执行前分组，动态轨迹用于执行后更新账本。

### 3.2 效应边界执行单元

Capsule 将相邻原子区域归并为有序执行单元：

$$
G = (g_1, g_2, \ldots, g_m), \quad
g_j = (r_{a_j}, \ldots, r_{b_j}).
$$

所有单元构成原子区域的无重叠有序划分，满足：

$$
\operatorname{concat}(g_1.\text{source}, \ldots, g_m.\text{source}) = P.\text{source}.
$$

这里的 $g_j$ 称为效应边界执行单元，而不是“任务语义单元”。边界来自源代码结构、定义—使用关系、控制流和环境声明的副作用函数。该名称刻意避免声称每个分组具有任务级前置条件或后置条件。

### 3.3 历史副作用与合法恢复

运行时维护副作用账本 $L_t$。当执行单元 $g_j$ 已调用机器人副作用函数时，其标识被加入账本：

$$
L_{t+1} = L_t \cup \{g_j\}.
$$

账本中的单元是历史副作用单元。本文采用以下前向恢复约束：

1. $g_j \in L_t$ 时，不允许再次执行 $g_j$；
2. $g_j \in L_t$ 时，不允许修改后把 $g_j$ 当作原历史片段重新执行；
3. 恢复程序 $P_{\mathrm{rec}}$ 只能作为新的源码追加，并从当前物理状态 $s_t$ 开始；
4. $P_{\mathrm{rec}}$ 必须至少调用一个由当前 API 声明的新观测函数 $a_{\mathrm{obs}} \in \mathcal{A}_{\mathrm{obs}}$，之后才能产生新的机器人副作用。

合法恢复可以写为：

$$
P_{\mathrm{rec}} \in \mathcal{R}(s_t)
\iff
\operatorname{Parse}(P_{\mathrm{rec}})=\mathrm{true}
\land
\operatorname{Calls}(P_{\mathrm{rec}}) \cap \mathcal{A}_{\mathrm{obs}} \neq \varnothing.
$$

这一约束不保证恢复一定成功；它只排除两类与物理状态不一致的操作：盲目重放历史副作用，以及不刷新状态便继续使用旧观测。

### 3.4 研究范围

本文不假设任意 MuJoCo 状态回滚，更不假设真实机器人能够恢复到历史精确状态。Capsule 也不学习新的低层控制器，不验证 API 的物理安全性，不把奖励上升视为每个单元的可靠后置条件。系统目标是为现有 CaP 程序提供可观测、可约束的执行恢复层。

## 4 Capsule 方法

### 4.1 总体架构

![Capsule 运行时控制架构](../figures/capsule-runtime-control-architecture.svg)

> 图 1 为当前工程架构图占位版本，其中的 “semantic groups” 在本文统一解释为效应边界执行单元；投稿前需更新图中文字，避免暗示执行单元具有未经验证的任务语义。

Capsule 位于语言模型生成程序和机器人环境 API 之间。模型首先生成完整的 CaP 风格 Python 程序，程序仍调用 `get_object_pose`、`goto_pose`、`open_gripper` 等环境原有函数。运行时只向控制模型暴露 `run_group`、`patch_group`、`inspect_trace`、`inspect_variables`、`append_recovery` 和 `finish` 等代码执行动作；这些动作本身不直接移动机器人。

系统包含五个主要部分：源码分段与分析、效应边界归一化、持久执行器、追踪与反馈、副作用账本与恢复控制。正常路径在自动前向模式下按源序执行；模型只在初始语法错误、运行异常、禁止重放、粗粒度保护条件或终止恢复阶段介入。

### 4.2 原子区域分析与效应边界归一化

Capsule 首先使用 Python AST 将程序切分为顶层原子区域。每个区域记录源码行、定义变量、使用变量、直接原语调用、控制流形态和结构化副作用。对于本地定义的辅助函数，分析器在能够静态解析时把函数体的副作用信息传播到调用点；无法解析的动态调用保留原结构事实，不进行无依据推断。

归一化层仅产生分组元数据。其核心不变量是源码字节和区域顺序不变，所有区域恰好属于一个执行单元。分组优先在机器人副作用处保留边界，并使用定义—使用关系避免跨越会削弱修复粒度的依赖点。若依赖信息不明确，系统保守地保留边界。当前实现使用宽松的组数范围抑制“一个巨大单元”和“十余个微小单元”两种极端，但该范围是工程策略参数，不是语义正确性的判据。

### 4.3 持久命名空间与自动前向执行

执行器在整个试次中维护同一 Python 命名空间，使前序区域计算的对象位姿、抓取姿态和中间变量可供后续区域使用。对于效应边界单元 $g_j$，执行器按成员区域顺序编译并运行原始源码，记录标准输出、异常、返回状态和局部追踪窗口。

推荐的 `auto_forward` 模式按以下流程工作：

1. 生成并解析初始程序；
2. 构建效应边界执行单元；
3. 按源序自动运行下一个尚未执行的单元；
4. 成功后更新追踪与副作用账本，并继续下一个单元；
5. 失败或触发保护条件时，构建有界恢复上下文并请求一次恢复动作；
6. 恢复源码通过验证后重新分段，只执行新追加的恢复单元；
7. 任务完成、模型选择结束、预算耗尽或无合法恢复时停止。

系统保留 `llm_step` 模式作为兼容和消融路径。在该模式中，模型可逐步选择运行、检查或修补动作。由于它在正常执行的每个微步骤都需要模型调用，本文不将其作为推荐部署模式。

### 4.4 原语追踪与源代码绑定反馈

环境构建 Capsule 命名空间时，为公开 API 函数增加内部追踪包装器。包装器保留原函数名称、参数和返回语义，只记录调用名称、参数摘要、返回摘要、异常和时间顺序。生成程序仍调用原函数，不感知新的机器人工具接口。

每次执行前，追踪器记录窗口起点；执行结束后，反馈模块只提取当前区域或单元产生的局部事件。反馈包括：

- 单元与成员区域标识；
- 源码起止行；
- 执行状态和异常摘要；
- 局部原语调用及失败事件；
- 执行前后任务奖励与完成状态；
- 允许的修补或前向恢复范围。

对于数值可观测性，小型数组可以序列化为有界列表；RGB、深度图、掩码和点云等大型数组仅保留形状和类型摘要。追踪摘要只包含事件计数、函数调用频次、最近事件和失败事件，避免完整历史随步骤数无限增长。

反馈中的奖励变化只作为粗粒度证据。感知、规划或预抓取单元即使没有即时奖励提升，也可能正确完成，因此系统不把“奖励不变”统一解释为失败。本文也不声称已经为每个执行单元定义可靠的任务后置条件。

### 4.5 副作用账本与禁止重放

Capsule 同时使用静态标记和动态追踪维护副作用账本。若单元被静态判定包含机器人动作，或者其实际轨迹调用了环境声明的副作用函数，运行时就把该单元及相应成员区域登记为已经执行。

在后续动作分发前，系统检查目标是否位于副作用账本中。对历史副作用单元发起 `run_group`、`run_region`、`patch_group` 或 `patch_region` 时，运行时返回结构化非法事件，并建议基于当前状态追加恢复。该守卫不是提示词建议，而是运行时强制约束。无机器人副作用的计算单元仍可在逐步模式中检查或修补，因为其重新执行不会直接改变物理世界；但开发者仍需注意外部 I/O 等未声明副作用。

### 4.6 基于新观测的追加恢复

当历史动作已经改变环境时，Capsule 使用 `append_recovery` 添加新代码。该动作首先检查：参数中存在非空源码、源码能够被 Python AST 解析、当前 API 声明了至少一个恢复观测函数，以及源码确实调用其中至少一个函数。验证失败不会修改已保存程序。

恢复观测能力由环境 API 显式声明。默认情况下，若 API 公开 `get_observation()`，它可以作为新观测函数；任务特定 API 也可以声明抓取位姿或手柄位置等无副作用感知函数。这样，恢复规则不会在不存在 `get_observation()` 的环境中强制调用未定义名称。

追加成功后，系统重新执行分段和效应边界归一化，但不改变历史单元状态。新恢复单元从当前命名空间和当前物理状态开始。若恢复再次产生副作用，它也会被加入账本。由此形成单调向前的物理执行历史。

### 4.7 语法错误、非法补丁与终止

若初始程序存在语法错误，正常 AST 分段无法开始。Capsule 将完整源码临时表示为一个区域和一个执行单元，并把语法错误行、列和文本加入第 0 步诊断。模型可用 `patch_group` 替换完整源码。所有区域和单元补丁在发布前都要先构造完整候选程序并执行 AST 解析；非法候选只返回反馈，不覆盖最后一个有效程序。

运行时还处理无效动作、缺失参数、未知单元、恢复代码缺少新观测、模型服务失败和试验预算耗尽。结构化结果区分任务正常结束、执行失败、预算耗尽、提供商失败与实验基础设施失败。对于终止状态，系统可允许一次受限的追加恢复；若无合法恢复或预算耗尽，则保存当前源码、追踪、提示与逐步指标后结束。

### 4.8 Capsule 与多轮重新生成的机制差异

| 比较轴 | 多轮重新生成 | Capsule |
|---|---|---|
| 模型输出 | 根据当前反馈重新生成剩余代码或结束 | 初始完整程序；异常时产生局部补丁或追加恢复代码 |
| 执行粒度 | 生成的代码块或轮次 | 效应边界执行单元 |
| 变量状态 | 依赖基线的轮次实现 | 试次内持久命名空间 |
| 反馈定位 | 通常面向整轮执行结果 | 绑定单元、区域与源代码行 |
| 历史机器人动作 | 可能由重新生成逻辑隐式处理 | 运行时账本明确禁止重放历史副作用 |
| 恢复起点 | 由模型根据上下文推断 | 新代码必须先读取当前状态 |
| 正常路径模型调用 | 每次重新生成时调用 | `auto_forward` 中成功单元无需逐步调用模型 |
| 当前证据 | 有开发期基线记录 | 有多任务运行记录，但缺少严格统一配对 |

## 5 实验设计

### 5.1 研究问题

实验围绕四个研究问题组织：

- **RQ1：** Capsule 在不同 Robosuite 操作任务上的任务完成情况如何？
- **RQ2：** 前向恢复在何种执行失败后被触发，现有档案能否确认恢复有效？
- **RQ3：** 失败主要来自算法未完成、Capsule 步预算、模型服务还是实验基础设施？
- **RQ4：** 与原始多轮重新生成相比，现有证据能够支持哪些有限判断？

### 5.2 任务与系统设置

## 6 结果与讨论

### 6.1 RQ1：多任务完成情况

| 任务 | 方法与协议 | 有效试次/目标种子 | 完成数 | 平均奖励 | 解释边界 |
|---|---|---:|---:|---:|---|
| Cube Stack | Capsule 首轮开发运行 E01 | 20/20 | 9 | 0.4512 | Git 提交未记录；流式调用 |
| Cube Stack | Capsule 最新运行选择 E02 | 20/20 | 17 | 0.8614 | 含重试；2 个超时；不是首次尝试率 |
| Cube Stack | 多轮重新生成 E03 | 10/10 | 6 | 0.6052 | 仅种子 11--20；非流式 |
| Cube Lifting | Capsule E06 | 16/20 | 13 | 待统一复算 | 4 个结果缺失，不能记作算法失败 |
| Cube Lifting | 多轮重新生成 E04--E05 | 20/20 | 18 | 待统一复算 | 两批同类设置，需从原始记录复算总均值 |
| Cube Restack | Capsule E07 | 20/20 | 4 | 0.277433 | 提交 `7058f82` |
| Two-arm Lift | Capsule E10--E11 | 20/20 | 11 | 约 0.41394 | 同提交、API、超时和预算，可合并 |
| Two-arm Handover | Capsule E08 | 20/20 | 0 | 0.024035 | 17 个预算耗尽，3 个正常结束 |
| Two-arm Handover | Capsule E09 | 10/10 | 0 | 0.169420 | 提交和超时与 E08 不同 |

结果首先说明 Capsule 运行时能够在多种任务中执行模型生成的程序并形成代码、追踪、反馈和视频档案，但不能说明其性能在任务间稳定。Cube Stack 的重试包容结果达到 17/20，而 Cube Restack 和 Two-arm Handover 明显更弱；Two-arm Lift 处于两者之间。这一差异与任务所需的接触、双臂协调、视觉估计和长时程依赖可能有关，但当前实验同时改变了 API、提交和超时，尚不能把差异归因于单一机制。

Cube Stack 的 E01 与 E02 还展示了结果选择规则的重要影响。首轮开发运行仅完成 9/20；后续多批重试并按每个种子选取最新结果后完成 17/20。该变化可能同时来自代码修复、非流式调用、服务稳定性和多次尝试。因而，E02 可以描述系统在当前重试流程下获得的覆盖结果，但不能替代首次尝试性能或公平成本比较。

### 6.2 RQ2：恢复行为与有效性

Capsule 档案包含 `capsule_trace_trial_XX.json`、`capsule_prompts_trial_XX.json`、`capsule_step_metrics_trial_XX.jsonl` 和最终源码，可用于重建恢复链。现有代码还记录 `append_recovery_source_appended`、恢复执行是否改善奖励以及副作用单元集合。这些字段提供了验证前向恢复机制的必要观测接口。

然而，历史运行跨越多个结果 schema，当前尚未形成统一的恢复聚合表。因此，本文只能确认系统实现并记录了追加恢复路径，不能给出“恢复触发后有多少比例最终成功”或“恢复导致多少奖励提升”的可靠数字。【恢复有效率待统一复算】终稿应至少报告：恢复触发次数、合法追加次数、追加后机器人执行次数、奖励改善次数、最终任务完成次数，以及因缺少新观测、语法错误、禁止重放或预算耗尽而失败的次数。

在机制层面，追踪档案可以支持案例分析，但单个成功视频不能证明普遍有效。建议从同一提交中选择三类轨迹：一次有效前向恢复、一次合法但未改善任务的恢复，以及一次因预算或观测不足而停止的恢复。每个案例都应给出失败单元、历史副作用、恢复观测、追加源码和后续状态，而不能只展示最终成功片段。

### 6.3 RQ3：失败类型

Two-arm Handover E08 的 20 个试次中，3 个正常结束、17 个耗尽试验预算，且没有任务完成。这一结果表明失败不能只用“成功/失败”二分：大部分试次未在给定 Capsule 步预算内形成有效终止。E09 把超时提高到 750 s 且更换代码提交后，平均奖励提高到 0.169420，但 10 个试次仍未完成任务。由于提交与种子集合同时变化，该观察不能证明单纯增加超时改善了策略。

Cube Lifting Capsule E06 的 20 个目标种子中只有 16 个有效结果，其中 13 个完成、3 个未完成。其余 4 个缺失记录可能来自提供商、父进程守卫或实验基础设施，必须回到日志分类。若直接以 20 为分母，会把未知基础设施状态混入算法成功率；若只报告 13/16，也会隐藏实验系统的产出损失。终稿应同时报告有效试次性能和端到端试验产出率。

当前结果聚合器已经区分提供商失败、算法失败、预算耗尽、基础设施失败和未分类失败，并能按试次聚合多次尝试。历史数据需要迁移到该 schema 后，才能回答不同失败桶的真实比例。

### 6.4 RQ4：与多轮重新生成的有限比较

Cube Stack 的多轮基线 E03 在种子 11--20 上完成 6/10，平均奖励为 0.6052。相同种子范围的早期 Capsule 首轮记录约完成 4/10，而 E02 中按最新运行选取的 Capsule 结果为 8/10。三个数字分别对应不同调用模式、代码状态和重试策略。因此，它们只能说明 Capsule 的开发期结果覆盖了低于和高于该基线的区间，不能支持“Capsule 优于基线”或“Capsule 弱于基线”的稳定判断。

Cube Lifting 多轮基线的两批结果合计完成 18/20；Capsule 有效记录完成 13/16，但有 4 个缺失结果。即使忽略缺失，方法的结果 schema、重试和提交信息也未完全对齐。该结果提示 Capsule 当前并未在简单任务上展示明确优势，终稿应通过统一配对实验而不是选择已有最优子集来判断相对效果。

机制比较仍有意义：多轮重新生成允许模型整体改写后续代码，Capsule 则保留局部变量和执行证据，并通过运行时守卫禁止历史副作用重放。前者提供更大的生成自由度，后者提供更明确的物理历史约束。二者的取舍应通过同预算实验同时考察成功率、机器人动作数、模型调用、token、恢复次数和墙钟时间。

### 6.5 讨论

现有结果支持两项有限判断。第一，Capsule 的运行时机制能够跨多种 Robosuite API 工作，并保存足够的程序级和执行级证据用于失败分析。第二，系统性能高度依赖任务、感知与运行协议；前向恢复约束本身并不保证模型能够生成正确恢复策略。

前向恢复的价值主要是排除不一致的执行历史，而不是自动提高所有任务的成功率。禁止重放可能减少某些危险或无效行为，但也收紧了模型的修复空间；若初始副作用已经把环境推进到难以恢复的状态，系统可能只能结束试次。类似地，要求新观测可以减少旧状态依赖，却不能保证观测准确、抓取候选有效或后续规划可行。

任务结果还受到底层模块影响。非特权环境依赖 RGB-D 感知、分割、抓取估计和运动规划；任何模块失败都可能表现为 Capsule 无法完成。Two-arm 任务还引入协同抓取、双臂可达性和更长程序依赖。未来实验需要把运行时恢复错误与感知、规划、控制和基础设施错误分别统计。

## 7 局限性

**文献范围。** 本文初稿只使用用户限定的 5 篇 2026 年预印本，尚未覆盖 CaP、程序修复、运行时验证和机器人安全恢复的经典文献。论文的新颖性边界仍需系统检索，当前不使用“首次”表述。

**实验一致性。** 现有档案来自开发过程，横跨多个 Git 提交、流式模式、超时、重试和结果 schema。除明确标记的子集外，数值不能直接比较。当前没有统一配对消融和统计检验。

**恢复有效性。** 系统已经记录恢复轨迹和若干效果字段，但历史档案尚未统一复算。本文不能声称追加恢复提高成功率，也不能把奖励变化解释为严格因果效应。

**任务与环境。** 当前证据主要来自 Robosuite 仿真操作任务，尚不足以说明开放环境、长期运行或真实机器人中的安全性与外部效度。【真实机器人实验待补或删除相关表述】

**接口依赖。** Capsule 依赖环境准确声明机器人副作用和新观测函数。未声明的外部 I/O、副作用遗漏或错误分类可能破坏禁止重放语义。固定 API 也限制模型能够表达的新行为。

**状态与安全。** 前向恢复不等于安全保证。系统不验证追加代码的碰撞风险、力限制和任务级安全约束，也不恢复到历史物理状态。真实部署仍需要独立安全控制器、急停、工作空间限制和可验证重置机制。

**模型与服务。** 结果依赖 DeepSeek V4 Flash、服务提供商状态、提示词、输出解析和 token 预算。当前档案中存在超时与缺失结果，端到端可靠性不能仅由有效试次成功率表示。

## 8 结论

本文针对包含不可逆物理副作用的 CaP 程序，提出效应边界前向恢复问题，并设计 Capsule 运行时。Capsule 保留原有机器人 API，以元数据方式构造效应边界执行单元，在持久命名空间中执行程序，将原语轨迹和状态证据绑定到源码范围，并使用副作用账本禁止历史机器人动作被重放。失败后的恢复代码必须重新观测当前状态并作为新源码向前执行。

对现有 Robosuite 档案的审计表明，Capsule 可以在多个操作任务上运行并形成可追溯的恢复证据，但任务结果差异明显：重试包容的 Cube Stack 集合完成 17/20，协议一致的 Two-arm Lift 集合完成 11/20，Cube Restack 完成 4/20，而 Two-arm Handover 的主要集合没有完成任务。这些结果主要验证系统可运行性和失败分析能力，尚不能证明 Capsule 相对多轮重新生成提高成功率。

后续工作应在固定代码提交和统一协议下开展配对实验，分别报告首次尝试、重试预算、恢复有效率、token、墙钟时间和机器人动作成本，并加入禁止重放、新观测约束、追踪反馈与自动前向模式的消融。真实机器人实验还需结合独立安全控制和可验证重置，才能判断前向恢复在物理部署中的适用范围。
